# commit-guard-action

Central, versioned commit guard for the whole fleet. One definition, one
place to fix a bug or add a rule, propagated automatically to every repo
that calls it.

It checks that commits carry **no AI attribution** (trailers, "generated by"
banners, bot author identities) and that **no credentials** were added.

## Use it

Drop this into a repo as `.github/workflows/post-commit.yml`:

```yaml
name: post-commit
on:
  pull_request:
    types: [opened, synchronize, reopened]
  push:
    branches: [main, master]
permissions:
  contents: read
jobs:
  commit-guard:
    uses: kodflow/commit-guard-action/.github/workflows/commit-guard.yml@main
```

That is the whole integration. It is pinned to `@main` on purpose: the logic
lives here, and a fix lands in every repo on its next run. **Do not copy the
script into your repo** — that is exactly the per-repo drift this replaces.

### Inputs

| Input | Default | Meaning |
|---|---|---|
| `strict` | `false` | Also apply `patterns-strict.txt` — bare vendor keywords, `.claude/` path leaks, `Plan:` footers. |
| `secrets_scan` | `true` | Scan added diff lines for credential shapes. |
| `guard_ref` | `main` | Ref of this repo to load logic from. Pin to a tag to freeze. |

Turn on `strict` only for repos where a commit message has no legitimate
reason to mention the tooling:

```yaml
    with:
      strict: true
```

## What CI can and cannot do

This is a port of `kodflow/ktn-linter`'s `scripts/git-guard.sh` (hardened
over three CodeRabbit rounds in PR #447), but the two operate at different
points and are **not** interchangeable.

That script is a Claude Code `PreToolUse` hook. It inspects a *git command
line before it runs*, so it can refuse `--no-verify`, rewrite `--force` into
`--force-with-lease`, and stop a bad commit from ever existing.

This workflow only ever sees commits that **already exist and are already
pushed**. That means:

| Check | Local hook | This action |
|---|---|---|
| AI attribution in the message | blocks the commit | fails the run |
| AI author identity | — | fails the run |
| Secrets in the change | blocks the commit | fails the run |
| `--no-verify` bypass | refuses it | **invisible** — leaves no trace in the commit |
| `--force` → `--force-with-lease` | rewrites it | **cannot** — the push already happened |

Consequences worth being explicit about:

- **On a pull request**, wiring this as a required status check genuinely
  blocks the merge. This is the intended use.
- **On a direct push to the trunk**, the workflow can only fail *after the
  fact*. There is no server-side rejection without pre-receive hooks, which
  require GitHub Enterprise. This deployment does not have it.
- We chose to **fail loudly and leave the commit alone** rather than have a
  bot auto-strip the offending lines. Auto-stripping a pushed commit means
  rewriting it and force-pushing over the trunk, which is a worse failure
  mode than a red check.

The local hook and this action are complementary, not redundant. Keep both.

## Historical audit

`.github/workflows/audit.yml` scans `git log --all` and reports every commit
already carrying attribution. It is **report-only** and deliberately not
wired to `push`/`pull_request`.

Run it manually (`workflow_dispatch`), or call it on a schedule:

```yaml
on:
  schedule: [{cron: '0 3 * * 1'}]
jobs:
  audit:
    uses: kodflow/commit-guard-action/.github/workflows/audit.yml@main
```

### Cleaning a tainted history

The audit **never rewrites anything**, by design. Cleaning historical commits
means a full-history rebase and a force-push, which:

- changes every commit SHA in the repo,
- breaks every open PR and every existing clone and fork,
- is irreversible once pushed over published work.

That is a deliberate, per-repo decision. If you want it for a given repo, do
it explicitly and consciously — typically with `git filter-repo
--message-callback` on a fresh mirror, verified before pushing. It is not
something a scheduled job should ever do on its own.

## Layout

```
scripts/ci-guard.sh          the logic
scripts/patterns.txt         default forbidden patterns (attribution-shaped)
scripts/patterns-strict.txt  opt-in extra patterns (keywords, workflow leaks)
.github/workflows/commit-guard.yml   reusable — what repos call
.github/workflows/audit.yml          reusable — history report
.github/workflows/ci.yml             self-test (shellcheck + behaviour tests)
stub/post-commit.yml         the file deployed into each repo
tests/run.sh                 behaviour tests against real throwaway repos
```

## Adding a rule

Edit `scripts/patterns.txt`, add a case to `tests/run.sh`, open a PR. Once
merged to `main` it is live everywhere on the next run.

Default patterns match the **shape of an attribution** — a trailer, a
"generated by" banner, a bot identity — not the mere mention of a vendor.
A bare `claude[- ]code` keyword would fail every legitimate PR on the repos
whose subject matter *is* the tooling. Keyword matching lives in
`patterns-strict.txt`, opt-in.
